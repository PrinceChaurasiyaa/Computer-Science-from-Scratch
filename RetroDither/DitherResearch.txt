========================== Google ============================================

A dithering algorithm is an image and audio processing technique that adds controlled noise to randomize quantization errors, creating the illusion of a broader color palette or smooth gradients on limited-display devices.

How It Works

Quantization Reduction: 
Reduces the number of colors or shades (such as turning a 24-bit image into a 16-color or black-and-white file).

Human Visual System: 
Relies on the human eye to blend tightly packed dots of available colors into intermediate tones and shades.

Banding Prevention: Eliminates harsh visual blocks or abrupt color steps (color banding) across smooth transitions.

Common Types of Dithering Algorithms

Ordered Dithering: Uses a repeating matrix (like a Bayer matrix) to compare pixel values against deterministic thresholds, making calculations fast and independent.

Floyd-Steinberg: A popular error-diffusion algorithm that calculates the difference between a pixel's true value and its reduced value, then spreads that leftover error onto neighboring unquantized pixels.

Random Dithering: Adds completely random noise to the signal or image before reducing colors, which prevents repeating grid patterns but can look overly grainy.

======================= Error diffusion =============================================

Error-diffusion is a digital halftoning technique used to convert continuous-tone images (like grayscale or color photos) into a limited color or binary (black-and-white) palette while preserving the illusion of intermediate shades.

How Error-Diffusion Works

Quantization: The algorithm scans an image pixel by pixel (usually left-to-right, top-to-bottom) and rounds each pixel's value to the nearest available color or brightness level in the target palette (e.g., pure black 0 or pure white 255).

Error Calculation: It computes the difference (the "quantization error") between the original pixel value and the new quantized value.

Error-Diffusion: This error is then distributed (or diffused) onto neighboring, unprocessed pixels using specific fractions or weights, compensating for the adjustment in subsequent steps.

Key Concepts and Algorithms

Floyd-Steinberg Dithering: The most famous error diffusion method. It pushes the residual error of a pixel to four immediate neighbors: 7/16 to the right, 3/16 to the bottom-left, 5/16 straight down, and 1/16 to the bottom-right.

Noise Shaping: Instead of creating harsh periodic patterns like traditional ordered dithering, error diffusion pushes quantization noise into higher spatial frequencies where the human eye is less sensitive, resulting in sharper detail and smoother gradients.

Advanced Variations: Methods like Jarvis, Judice, and Ninke or Stucki expand the error distribution kernel to a larger neighborhood (12 or more pixels) for higher visual quality at a greater computational cost.



=================== Steps ==============================

1. Find whether black or white is closer to the gray in the pixel. This 
will be based on some kind of threshold. For instance, if the grays are 
stored as 8-bit unsigned integers, there may be 256 shades of gray num
bered 0 through 255, and our threshold could be 127. Any pixel greater 
than 127 may be marked as white (255 in this scheme), and any pixel 
less than or equal to 127 may be marked as black (0).

2. Subtract the difference between the new pixel color and its original 
color. Imagine the original gray was 204. The difference would be  
255 – 204 = 51. This is our error.

3. Add one-eighth of the error to six specific pixels close to the original 
pixel. This is the diffusion step. In this case, 51 // 8 = 6 (we need to do 
integer division). The pixels adjusted are: one to the right, two to the 
right, one diagonally down and left, one diagonally down and right, 
one straight below, and one two below.

1. What is MacPaint?

MacPaint was a painting program created by Bill Atkinson and released by Apple in 1984 with the original Macintosh.

It was revolutionary because people could use:

A mouse 🖱️
A graphical user interface (GUI)
Tools for drawing and editing images

Before this, computers often required text commands, and graphical interaction was less common.

2. Why was MacPaint limited to black and white?

The original Macintosh had limited hardware capabilities.

MacPaint supported only:

Black = 1
White = 0

It did not support grayscale or color in its original format.

The image dimensions were fixed:

576 pixels wide X 720 pixels tall

That means:

Width  = 576 pixels
Height = 720 pixels

Total pixels:

576 X 720 = 414720

So a MacPaint image contains 414,720 pixels.

This is an important connection to your dithering studies.

Normally, a grayscale image uses 8 bits per pixel:

0 → Black
255 → White

For example:

pixel = 180

But MacPaint only needs two colors:

Black = 1

A single bit can represent each pixel.

That saves storage space.

4. What is run-length encoding (RLE)?

The paragraph says MacPaint used a compression technique called run-length encoding.

RLE compresses repeated values.

Example without compression

Suppose the pixel sequence is:

There are many repeated zeros and ones.

Instead of storing every bit individually, we can represent runs:

8 zeros, 8 ones, 8 zeros

Conceptually:

(0, 8), (1, 8), (0, 8)

This means:

8 consecutive zeros
8 consecutive ones
8 consecutive zeros
Why is this useful?

Images often contain repeated pixel patterns, such as large white backgrounds.

RLE can reduce the amount of data needed to store those patterns.

Important: The exact MacPaint RLE format has its own rules. The example above explains the general concept, not the complete MacPaint encoding specification.

7. What are Mac OS forks?

This is probably the most unfamiliar concept in the paragraph.

The classic Mac operating system stored files using two parts called forks.

1. Data fork

Contains the actual data of the file.

For a MacPaint file, this includes image-related data.

2. Resource fork

Contains additional structured resources, such as information used by applications.

Historically, Macintosh files could use both forks.

Why does this matter?

Modern operating systems, such as Windows and Linux, do not use the classic Macintosh fork system in the same way.

When a classic Mac file is transferred, information from its forks may need special handling.

That's why the book introduces MacBinary.

=============================== Bit Map ====================================

A bitmap is a digital image or memory map made of a grid of tiny dots called pixels, 
where each dot stores specific color information.


How Bitmaps Work

Pixels: 

The grid has rows and columns. Every single pixel holds a color value (like red, green, and blue).

Resolution: More pixels mean a sharper picture. If you zoom in too close, the image gets blurry and you see individual squares.

File Types: Common bitmap (raster) formats include JPEG, PNG, GIF, and BMP. Digital photos and scanned images are always bitmaps.


Bitmap vs. VectorBitmap: 

Stores color data for every single pixel. Great for photos, but files get very large and lose quality when enlarged.

Vector: Uses math lines and curves instead of a grid. Great for logos, because you can resize them infinitely without losing quality.

====================================  Translating Bytes to bits ===============================

In "L" mode, our Pillow Image is encoded using 1 byte per pixel. However, in 
a MacPaint bitmap, pixels are encoded with 1 bit per pixel, meaning each 
byte represents eight pixels. This is a big savings for black and white, and it 
makes total sense since we only need two values (1 and 0) to represent two 
colors.

1. Pillow "L" mode

Each pixel uses 1 byte:

[0, 255, 0, 255, 0, 255, 0, 255]

Each value occupies 8 bits:

1 pixel = 1 byte
2. MacPaint format

Each pixel uses 1 bit:

[0, 1, 0, 1, 0, 1, 0, 1]

 NOTE: 

means converting byte-per-pixel data into bit-per-pixel representation, then storing those packed bits inside bytes.

our first function in macpaint.py is a 
converter that takes the byte array we got from dither() and converts it into 
a “bit array”:

Convert an array of bytes where each byte is 0 or 255
to an array of bits where each byte that is 0 becomes a 1
and each byte that is 255 becomes a 0

=====================================  Run-Length Encoding ======================================================

Storing pixels as individual bits rather than bytes saves a significant amount 
of space, but it’s not enough. When MacPaint launched in 1984, the origi
nal Macintosh had floppy disks that supported just 400KB of data. There 
was no hard drive, and a standard configuration had just one floppy drive. 
Think about how big a MacPaint file would be if it weren’t compressed. The 
576 pixels in a row take up 576 bits, which is 72 bytes. There are 720 rows, so 
720 multiplied by 72 bytes is 51,840 bytes. Adding in the 512-byte header, a 
MacPaint file would be 52,352 bytes with no compression. That would mean 
a floppy disk couldn’t even store eight MacPaint files!
To relieve this disk space problem, the MacPaint file format incorporates 
a simple compression scheme called run-length encoding. In this scheme, 
instead of repeating the same thing, you say how many times it should repeat. 
For example, suppose we want to store the string AAAAAABCCCCCABBBB. 
If each character uses 1 byte, it would be 17 bytes. Would it not be more effi
cient to say seven As instead of repeating A seven times? Or saying five Cs?
Suppose we use up to 1 byte before a character to store its number 
of repetitions. The string could then be encoded as 6AB5CA4B, which is 
8 bytes. However, there’s a problem with this scheme. Remember, in com
puter memory these would be raw bytes. How do we know that B is a char
acter and not a byte indicating a certain number of repetitions of the next 

character? In other words, B would likely be stored in memory using its 
ASCII/Unicode code, 66. Our program would likely interpret it as indicat
ing 66 of the next character, not a single letter B.
We could instead have a scheme where every character is preceded by 
a number, even single characters. This would change the encoded string 
to 6A1B5C1A4B. That’s 10 bytes, a 7-byte savings over the original, which 
is significant.
This encoding scheme is a form of run-length encoding, but it breaks 
down pretty quickly: for many strings, it’s actually less efficient than just 
storing the raw characters. For example, the string ABC would be 1A1B1C. 
That’s double the size.
There’s a compromise. You can have an encoding scheme where each 
number indicates either a repetition or a certain number of literal char
acters. Then, ABC becomes 3ABC. That’s still longer, but this new scheme 
may be a good compromise for more complex cases. For instance, the string 
AAAAABCBCAAAAAA would be 5A4BCBC6A.
This version is close to the encoding scheme the MacPaint file format 
uses, but there’s still a problem: How would you know that the 5 means five 
As, but the 4 means a literal sequence of four characters (BCBC) rather 
than four Bs? You may say, “Well, you could read ahead two characters and 
see that C isn’t a number, so the 4 couldn’t mean four Bs,” but even that 
doesn’t work, because (again) in computer memory, the C is stored as a 
number. We need another improvement.
MacPaint eliminates the ambiguity between numbers that indicate lit
eral runs and numbers that indicate repetition runs by representing both 
using signed 1-byte integers. A number n between 0 and 127 indicates n + 1 
literal bytes follow. A number n between –1 and –127 indicates 1 – n repeti
tions of the following byte. The number –128 isn’t used. This compression 
scheme is known as PackBits,5 and it was used beyond just MacPaint in sev
eral other popular file formats.
A PackBits function was actually built into classic versions of Mac OS. 
According to Apple’s own technical note on the subject, “typical MacPaint 
documents compress to about 10K” with PackBits.6 Table 3-3 summarizes 
the PackBits encoding scheme.

1. Why do we need compression?

MacPaint uses a fixed image size:

Width = 576 pixels
Height = 720 pixels

Since each pixel uses 1 bit:

576 bits ÷ 8 = 72 bytes per row

Total image data:

72 × 720 = 51,840 bytes

Plus the 512-byte header:

51,840 + 512 = 52,352 bytes

Compression reduces this size, especially when many neighboring pixels are identical.

2. What is Run-Length Encoding (RLE)?

RLE means:

Instead of storing the same value repeatedly, store its value and how many times it repeats.

Without compression
AAAAAABCCCCCABBBB

Each character takes 1 byte.

With simple RLE
6A1B5C1A4B

Meaning:

6A → AAAAAA
1B → B
5C → CCCCC
1A → A
4B → BBBB

This saves space when values repeat frequently.

Problem

How do we know whether 6 means:

Six repetitions?
Six literal characters?

We need a way to distinguish the two cases.

3. PackBits solves the ambiguity

PackBits uses a control byte before each group.

The control byte tells us whether the following data is:

A literal sequence (different bytes copied directly).
A repeated sequence (one byte repeated multiple times).

There are two important ranges.

Case A: Literal bytes

Control byte:

0 to 127

The number n means:

Copy the next n + 1 bytes literally.
Example
2, A, B, C

Control byte = 2.

Calculate:

2 + 1 = 3 bytes

So copy:

A B C
Case B: Repeated byte

Control byte:

129 to 255

The number n means:

Repeat the next byte 257 - n times.
Example
254, A

Calculate:

257 - 254 = 3

So:

254, A

means:

A A A
Case C: Skip byte

Control byte:

128

This byte is ignored.

It does not represent a literal sequence or repetition.

4. Why are repetitions represented using 129–255?

The original specification uses signed 8-bit integers:

Signed value	Meaning
0 to 127	Literal bytes
-1 to -127	Repeated bytes
-128	Unused

But your Python program works with unsigned bytes (0–255).

To convert a negative signed byte to unsigned:

Unsigned value = Signed value + 256

Examples:

-1   → 255
-2   → 254
-3   → 253

The repetition count is:

1 - signed_value

Using unsigned values:

257 - unsigned_value
Example

Signed control byte:

-2

Means:

1 - (-2) = 3 repetitions

Unsigned representation:

-2 + 256 = 254

Therefore:

257 - 254 = 3

Both represent the same operation.

What is the purpose?
def run_length_encode(original_data: array) -> array:

This function compresses MacPaint's packed image bytes using PackBits Run-Length Encoding.

It handles two types of data:

Repeated bytes → compress them.
Different bytes (literal data) → store them as a group.
1. Understand the input

Suppose one row contains these packed bytes:

original_data = [170, 170, 170, 128, 0, 42, 170, 170]

We can divide it into:

170, 170, 170          → Repeated bytes
128, 0, 42             → Literal bytes
170, 170              → Repeated bytes

The encoder should produce:

254, 170               → Repeat 170 three times
2, 128, 0, 42          → Copy three literal bytes

Now let's understand the code.

2. The take_same() helper function
def take_same(source: array, start: int) -> int:
    count = 0

    while (start + count + 1 < len(source)
           and source[start + count] == source[start + count + 1]):
        count += 1

    return count + 1 if count > 0 else 0
Purpose

It checks how many identical bytes occur consecutively, starting from a specific position.

Example
source = [170, 170, 170, 128]
start = 0

Visualize:

Index:  0    1    2    3
Value: 170  170  170  128

The function compares:

source[0] == source[1]  → True
source[1] == source[2]  → True
source[2] == source[3]  → False

It finds 3 identical bytes.

take_same(source, 0)

Returns:

3
Why return 0 sometimes?

If the starting byte has no immediate duplicate:

source = [170, 128, 0]
take_same(source, 0)

returns:

0

This tells the main function:

There is no repeated run beginning here.

Now examine:

Meaning

=========================================== MacBinary ========================================

1. Why do we need MacBinary?

In modern operating systems, a file is generally one block of data:

myfile.txt
└── File data

But in classic Mac OS, files could contain two separate parts called forks.

Mac OS File
├── Data Fork
└── Resource Fork
Data Fork

Contains the main content of the file.

For our MacPaint project, it contains:

MacPaint Header + Compressed Bitmap
Resource Fork

Contains additional resources, such as:

Icons
Sounds
Images
Program resources

Our MacPaint file does not need a resource fork.

2. What problem occurs on other operating systems?

Classic Mac OS stores information differently from Windows and Linux.

When a Mac file is transferred to another operating system, its metadata and forks might be lost or damaged.

Therefore, a special packaging format called MacBinary was created.

MacBinary structure
MacBinary File
├── 128-byte MacBinary Header
├── Data Fork (MacPaint file)
└── Resource Fork (none in our case)

Think of MacBinary as a container that protects the MacPaint file and its metadata.

3. Why do we need type and creator codes?

Modern systems commonly use file extensions:

picture.png → Open with image viewer
document.pdf → Open with PDF reader

Classic Mac OS instead used two codes:

Code	Meaning
Type code	Identifies what kind of file it is
Creator code	Identifies which application created or opens it

For MacPaint:

Type code:    PNTG
Creator code: MPNT

Therefore, after the MacBinary file is unpacked on classic Mac OS:

PNTG + MPNT
       ↓
   MacPaint

The file can be opened by double-clicking, even without a .macpaint extension.

4. MacBinary header

The MacBinary header is exactly 128 bytes.

MacBinary File
┌───────────────────────────┐
│ Header (128 bytes)        │
├───────────────────────────┤
│ MacPaint Data Fork        │
├───────────────────────────┤
│ Padding (if necessary)    │
└───────────────────────────┘

The header contains information such as:

Filename
File type
Creator application
Data fork size
Creation time
Modification time

Most other header fields are filled with zeroes.

5. Understanding the header table

The table provides three key pieces of information:

Offset	Length	Meaning
1	1 byte	Filename length
2	1–63 bytes	Filename
65	4 bytes	File type
69	4 bytes	Creator code
83	4 bytes	Data fork length
91	4 bytes	Creation time
95	4 bytes	Modification time

Important: The offsets are traditionally numbered starting at 1, while Python array indexes start at 0.

So:

Table offset 1 → Python index 0
Table offset 65 → Python index 64
6. Filename length

The filename can contain up to 63 characters.

Example:

filename = "drawing"

Its length is:

len(filename)  # 7

The header stores:

Position 1: 7
Position 2: drawing

Conceptually:

Header
├── 07
└── drawing

The filename uses MacRoman encoding, which was a character encoding used by classic Mac OS.

7. File type: PNTG

This identifies the file format.

PNTG

It tells classic Mac OS:

This is a MacPaint graphic file.

It occupies exactly 4 bytes:

P → 1 byte
N → 1 byte
T → 1 byte
G → 1 byte
8. Creator code: MPNT

This identifies the application associated with the file.

MPNT

It tells the operating system:

MacPaint is the application associated with this file.

Both codes are stored as four characters.

Type:    PNTG
Creator: MPNT
9. Data fork length

The MacPaint file we created earlier contains:

MacPaint Header + RLE-compressed bitmap

The MacBinary header must record the size of this data fork.

For example:

Data fork length = 52,352 bytes

The value is stored using 4 bytes.

This allows the system to know where the data fork ends.

10. Why big-endian?

A number can be stored in different byte orders.

For example, consider the hexadecimal number:

0x12345678
Big-endian

Stores the most significant byte first:

12 34 56 78
Little-endian

Stores the least significant byte first:

78 56 34 12

Classic Mac OS used big-endian processors, so MacBinary expects multibyte numbers in big-endian order.

In Python, you can convert an integer into big-endian bytes using:

number.to_bytes(4, byteorder="big")

Example:

length = 1000

result = length.to_bytes(4, byteorder="big")
11. Why is padding necessary?

MacBinary files must have a total size that is a multiple of 128 bytes.

Suppose the complete file size is:

Header: 128 bytes
Data fork: 500 bytes

Total: 628 bytes

628 is not divisible by 128.

The next multiple of 128 is:

640 bytes

Therefore:

Padding = 640 - 628
        = 12 bytes

The final file becomes:

128-byte header
+ 500-byte data fork
+ 12-byte padding
= 640 bytes

The padding is generally filled with zeroes.

12. Complete conversion process

Your entire program follows this pipeline:

Original Image
      ↓
Dithering
      ↓
Black and White Pixels
      ↓
Pack 8 Pixels into 1 Byte
      ↓
Prepare 576 × 720 Bitmap
      ↓
PackBits Compression
      ↓
MacPaint File
      ↓
Create 128-byte MacBinary Header
      ↓
Add MacPaint Data Fork
      ↓
Add Padding to Multiple of 128
      ↓
Final MacBinary File
In one sentence

MacBinary wraps your MacPaint data fork inside a 128-byte header containing metadata, then adds padding so the complete file size is divisible by 128 bytes.


====================================== BIG-ENDIAN VS. LITTLE-ENDIAN ==========================================================================


What order should the bytes representing a piece of data, such as a number, 
be stored in? This is a much-debated question, with the computer science world 
split between two camps: big-endian and little-endian .
Think for a moment about how we represent numbers in everyday life . 
If you come from a culture that uses the Arabic numeral system, like the 
English-speaking world, you’re probably used to writing numbers from left 
to right starting with the digit representing the largest part of the number 
and decreasing from there . For example, the number 450 starts with the 
4 representing the hundreds place, then the 5 representing the tens place, 
and then the 0 representing the ones place . The 4 represents the largest 
part of the number (400) and comes first . The decision to put the 4 first was 
made a long time ago and is largely arbitrary . In theory, we could have a 
numeral system that writes 450 from smallest to largest as 054, but obvi
ously we don’t .
The number 450 requires 2 bytes to represent in binary: 00000001 
and 11000010 . If you know binary, you know that each 1 represents a single 
power of 2 that, added with the other “on” powers of 2, gives us the final num
ber . The first byte, 00000001, puts its lone 1 in the 28 place and represents 
256 . The second byte, 11000010, represents the number 194 because the 1s 
for 21 (2), 26 (64), and 27 (128) are turned on, and 128 + 64 + 2 = 194 . We 
have bytes for 256 and 194, and 256 + 194 = 450 .
Since we write 450 from largest to smallest, you might assume that your 
computer would similarly store the byte representing the larger portion of 450 
first, yielding 0000000111000010 when the bytes are put together . This is 
known as big-endian order, but it’s not how most computers actually work now
adays . The typical modern computer is built with a microprocessor that uses 
one of two architectures: x86-64 (Intel, AMD) or ARM64 (Apple, Qualcomm, 
and so on) . For technical and historical reasons, those architectures store num
bers in little-endian order, where the byte representing the smallest end of the 
number comes first . In a little-endian system, the 2-byte number 450 is stored 
as 1100001000000001 . It’s important to know which system is at play, since 
interpreting the little-endian 1100001000000001 as if it were in big-endian 
order would result in a completely different value .
While little-endian order dominates today’s computer architectures, certain 
systems, such as those that run on the 68K microprocessor architecture (origi
nally by Motorola)—including the original Macintosh—store their numbers in 
big-endian order . Yes, on the original Macintosh, 450 was stored “the right 
way” as 0000000111000010, but on the computer in front of you it’s prob
ably stored as 1100001000000001 . Further complicating matters, most data 
transmitted over the internet is sent in big-endian order . When you’re browsing 
the web on your x86-64 or ARM64 microprocessor, there’s endian conversion 
going on in the background



Putting It All Together
To write our MacPaint file bundled as a MacBinary file, we need to take our 
pixel array from dither() and:
1. Call prepare() to convert it from bytes to bits and pad it with 0s.
2. Call run_length_encode() to run-length encode the bit array.
3. Call macbinary_header() to combine the result with a MacBinary  
header.
4. Add a 512-byte MacPaint header as well.
5. Pad the end result with 0s up to a multiple of 128 bytes to follow the 
MacBinary specification requiring this.
